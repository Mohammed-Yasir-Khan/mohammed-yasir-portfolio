## The problem

Every release used to be a long manual checklist for the SRE team:

1. Snooze monitoring, otherwise the deployments trigger an alert storm.
2. Pause the test automation pipelines so they do not run in the middle of the release.
3. Switch off the Jira automation rules that would interfere.
4. Move release tickets forward batch by batch, watch each batch deploy, and stop to fix anything that fails.
5. Undo all of the above afterwards.

It was slow, repetitive and easy to get wrong at 2 a.m. The goal was simple: run a whole release from one place, safely, with clear notifications.

## What I built

There are three release types. Each has its own Jenkins job, and they share the same building blocks.

### Weekly patch release

One job per environment, started by a schedule, so nobody has to remember to trigger it. It runs four steps:

1. **Snooze** monitoring for the release window.
2. **Deploy patches:** pick up this week's patch tickets, move them from Backlog to Pre-Deploy in bulk, then wait until each one reaches the first test level (L0).
3. **Unsnooze** monitoring.
4. **Verify and report:** check that the backlog is empty, nothing is still snoozed and L0 is at 100 percent, then build an Excel report.

The job only asks for two inputs: the environment and a dry-run switch. Dry run is on by default, so a rehearsal changes nothing in Jira and snoozes nothing. Each run labels itself with its own date and time, so two runs in the same week never collide.

The master has no business logic of its own. It only conducts jobs that already exist, so each one is still usable on its own. Every section is optional: leave its input empty and that step is skipped.

### Major release

A separate master wrapper for one environment. It reuses the same child jobs and adds what only a major release needs: turn the maintenance page on, shut services down in a set order, deploy in batches, restore the services, run the first test level, validate, then turn the maintenance page off. The whole flow is listed in a config file, so the order can change without touching code.

## The batch engine

This Python script is the heart of the minor and major releases.

- You give it one release filter and an ordered list of batches.
- For each batch it moves the tickets to Pre-Deploy, then checks Jira every 10 seconds.
- Each ticket status falls into a bucket: **blocked** (a deployment failed), **approval gate** (a validation gate failed), **pending**, or **done**.
- A batch is finished when nothing is pending, blocked or waiting on approval. Then it moves to the next batch.

### What happens when something breaks

A failed ticket does **not** crash the release. The engine sends the on-call engineer the likely root cause (taken from the latest automation comment, with links to the pipeline), then waits. As soon as the ticket is fixed, it carries on by itself. A time budget is the only hard stop.

Approval-gate failures get the standard exception approval applied automatically, and the engineer is told.

## Design decisions

| Decision | Why |
|---|---|
| Master wrappers only trigger existing jobs | No copied logic, and each job stays independently useful |
| Dry run is on by default | Nobody changes production by accident |
| Wait and resume instead of fail | A fixable failure should not force a full re-run |
| Resume from a state file | A re-run skips batches that already finished |
| Clean up the pasted filter automatically | A filter that includes a status clause blinds the poller once tickets move on, and the batch would look complete too early. Stripping it fixed that class of bug |
| One notification stream from the master | Starting, done and failed messages without duplicates |
| Time-window governance | A real run outside its allowed window is refused |
| Settings live in config files | Moving a window or changing a status needs no code change |

## Safety and limits

- If a snooze step fails, the snooze wrapper un-silences every tool it touched, so monitoring is never left muted.
- A failure before the batch step stops the master immediately. It does not roll back earlier steps yet, by design, so the system might be partly prepared. The restore action cleans that up.
- Some checks report "not verified" instead of passing when the job cannot read the data. The report never claims a pass it could not prove.

## Result

Releases that needed a person clicking through many steps now run from a schedule or one button, with the same checks every time and a report at the end.
